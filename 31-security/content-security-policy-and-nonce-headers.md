# T3102 · Content Security Policy (CSP) Directives, Nonces & Hashes

**Difficulty:** Medium  
**Companies Asked:** Google, Meta, Amazon, Microsoft, Stripe  
**Interview Frequency:** ★★★★★  
**Category:** Security  
**Concepts:** security, csp, content-security-policy, xss-prevention, nonces  

## Question

How does a Content Security Policy (CSP) mitigate Cross-Site Scripting (XSS) and Data Injection attacks, how do fetching directives (`default-src`, `script-src`, `style-src`, `connect-src`) restrict resource loading, and how do Cryptographic Nonces (`nonce-<base64>`) allow inline script execution safely?

## Expected Answer

1. **Content Security Policy (CSP)**: An HTTP response header (`Content-Security-Policy`) sent by web servers allowing site administrators to restrict the origins from which browsers can load scripts, stylesheets, images, and network sockets.
2. **Core Directives**:
   - `default-src 'self'`: Default fallback policy for unspecified fetch directives.
   - `script-src 'self' https://trusted.cdn.com`: Restricts JavaScript file origins and disables inline scripts (`<script>alert(1)</script>`) and `eval()`.
   - `style-src 'self' 'unsafe-inline'`: Restricts CSS stylesheet origins.
   - `connect-src 'self' https://api.example.com`: Restricts origins for `fetch()`, `XMLHttpRequest`, and `WebSocket` connections.
3. **Cryptographic Nonces**: Random, cryptographically secure one-time strings generated by the server on every request (`nonce-rAnd0m123`). The server attaches `script-src 'nonce-rAnd0m123'` in the CSP header, allowing only inline `<script nonce="rAnd0m123">` elements with matching nonces to execute.

## Deep Explanation

### CSP Nonce Enforcement Flow

```
HTTP Response Header:
Content-Security-Policy: script-src 'nonce-a8f9x2' 'strict-dynamic';

Browser HTML Parser:
├── <script nonce="a8f9x2">console.log("Allowed!")</script> ---> EXECUTES (Nonce Matches!)
└── <script>alert("XSS Injected Payload")</script>          ---> BLOCKED! (No Nonce!)
```

## Production Example

```javascript
// Express.js CSP Header Security Middleware with Dynamic Nonce Generation
import express from 'express';
import crypto from 'crypto';

const app = express();

app.use((req, res, next) => {
  // Generate random 16-byte base64 cryptographic nonce per request
  res.locals.nonce = crypto.randomBytes(16).toString('base64');

  // Set Strict Content-Security-Policy Header
  res.setHeader(
    'Content-Security-Policy',
    `default-src 'self'; ` +
    `script-src 'self' 'nonce-${res.locals.nonce}' 'strict-dynamic'; ` +
    `style-src 'self' https://fonts.googleapis.com; ` +
    `font-src 'self' https://fonts.gstatic.com; ` +
    `img-src 'self' data: https://images.example.com; ` +
    `connect-src 'self' https://api.example.com; ` +
    `frame-ancestors 'none'; ` +
    `base-uri 'self'; ` +
    `form-action 'self';`
  );

  next();
});

// Render Server HTML template injecting the per-request nonce
app.get('/', (req, res) => {
  res.send(`
    <!DOCTYPE html>
    <html>
      <head>
        <title>Secure App</title>
      </head>
      <body>
        <div id="root"></div>
        <script nonce="${res.locals.nonce}">
          window.__INITIAL_STATE__ = { user: 'Alice' };
        </script>
      </body>
    </html>
  `);
});
```

## Best Practices

- Use `Content-Security-Policy-Report-Only` headers during initial CSP rollout to log policy violations to a reporting URL (`report-uri /csp-report`) without breaking site functionality.
- Never use `'unsafe-eval'` or `'unsafe-inline'` in production `script-src` directives unless paired with a strong nonce or SHA-256 hash.

## Common Mistakes

- Believing CSP replaces input sanitization — CSP is a **defense-in-depth secondary containment boundary**; input sanitization and context-aware escaping remain essential.
